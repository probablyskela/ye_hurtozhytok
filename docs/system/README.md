# Система

## Як це працює

```text
Телефон (PWA: manifest, service worker, пуші)
        │  HTML-форми + React (гідратація)
        ▼
Cloudflare Worker ── React Router v7 (loaders / actions, SSR)
        │  Drizzle ORM          │ Cron Trigger щохвилини
        ▼                       ▼
Cloudflare D1 (SQLite)    нагадування: Web Push + Telegram
        ▲
Telegram Bot API ── POST /telegram/webhook (вхід, повідомлення)
```

Один Worker віддає сторінки й обробляє форми, окремого API немає: кожен
маршрут має `loader` (читання) і `action` (зміни). Форми працюють і без
JavaScript. Стек і підходи ті самі, що в Опереті.

## Структура коду

```text
apps/web/app
  routes/              маршрути
  modules/laundry/     запис на пралки: правила, вільний час, записи
  modules/auth/        вхід через Telegram, сесії
  modules/notify/      Web Push, Telegram, нагадування
  lib/                 спільне: time.ts, permissions.ts, db/schema.ts
infra/d1/migrations    міграції, генеруються з db/schema.ts
```

Наступні частини (оголошення, дошка студради, оплата) — нові теки в `modules/`.

## Дані

| Таблиця              | Призначення                                                                    |
| -------------------- | ------------------------------------------------------------------------------ |
| `residents`          | `telegram_id` (унікальний), `telegram_username`, ім’я, кімната, роль, `blocked`, `session_version` |
| `machines`           | Назва як на наліпці, поверх, `status` (`working`; згодом `broken`), порядок    |
| `bookings`           | `machine_id`, `resident_id`, `date`, `start_min`, `end_min`, `status`, `reminded_at`, час створення й скасування |
| `login_requests`     | Одноразові запити на вхід через бота: хеш коду, `telegram_id`, термін дії      |
| `push_subscriptions` | Підписки Web Push: `resident_id`, `endpoint`, ключі                            |
| `settings`           | Години роботи, запас, ліміт записів, горизонт запису                           |
| `activity_log`       | Хто що змінив                                                                  |

### Час

Запис зберігає київську календарну дату `date` (`YYYY-MM-DD`) і хвилини від
півночі за Києвом `start_min`, `end_min`. Тому «18:00» лишається 18:00 і після
переходу на літній час. UTC обчислюється з цього лише для нагадувань, через
`lib/time.ts`. Запис не переходить через північ. Моменти подій (створено,
скасовано) — UTC у мілісекундах, як в Опереті.

### Статуси запису

`active` або `cancelled`. Чи запис уже минув, видно з часу, окремо не
зберігається. «Звільнити раніше» переносить `end_min` на найближчі наступні
15 хвилин від зараз.

Під оплату згодом додається статус `held` з `expires_at`: запис тримається
кілька хвилин, поки людина платить, а вебхук еквайрингу переводить його в
`active`. Тоді ж з’явиться таблиця `payments`.

## Запис і перевірка вільного часу

Правила (`modules/laundry/rules.ts`, чисті функції з тестами):

- початок кратний 15 хв; тривалість від 30 хв до 2 год 30 хв з кроком 30 хв;
- запис уміщується в години роботи й не переходить через північ;
- між записами на одній пралці щонайменше 15 хв запасу;
- не більше 3 незавершених записів на людину; дата — від сьогодні до 7 днів.

**Вільні початки.** Для пралки й дня беремо активні записи, розширюємо кожен
на запас з обох боків і перебираємо початки з кроком 15 хв: підходить той, з
якого `[start, start + тривалість)` не перетинається з жодним розширеним
записом. Сьогодні — лише початки не раніше поточного кроку.

**Запис без гонок.** Перевірка й вставка — одна SQL-інструкція, тому двоє
людей не займуть той самий час навіть одночасно (D1 виконує записи послідовно):

```sql
INSERT INTO bookings (machine_id, resident_id, date, start_min, end_min, status, created_at)
SELECT :machine, :resident, :date, :start, :end, 'active', :now
WHERE NOT EXISTS (
  SELECT 1 FROM bookings
  WHERE machine_id = :machine AND date = :date AND status = 'active'
    AND start_min < :end + :buffer AND end_min + :buffer > :start
)
AND (SELECT count(*) FROM bookings
     WHERE resident_id = :resident AND status = 'active'
       AND (date > :today OR (date = :today AND end_min > :now_min))) < :limit;
```

Якщо вставлено 0 рядків, сервер з’ясовує причину (час зайняли чи вичерпано
ліміт) і показує її людині.

## Вхід через Telegram

Віджет Telegram Login не підходить: у встановленій PWA на iPhone він
відкривається спливаючим вікном і просить номер телефону. До того ж на iOS
PWA має власні cookie, окремо від Safari. Тому вхід іде через бота й опитування:

1. `POST /login` створює випадковий код, зберігає в `login_requests` лише
   його хеш, кладе код у підписане httpOnly cookie і відкриває
   `t.me/<бот>?start=<код>`.
2. У боті людина тисне «Start». Бот відповідає «Увійти в єГуртожиток?» з
   кнопкою «Так, це я»; після натискання записує `telegram_id` у запит.
3. Сторінка `/login/wait` у тому самому браузері чи PWA опитує сервер.
   Код береться з cookie, тож завершити вхід може лише пристрій, що його почав.
   Сервер створює чи знаходить мешканця за `telegram_id`, ставить cookie
   сесії й видаляє запит. Без JavaScript — кнопка «Я підтвердив у Telegram».
4. Новий мешканець вказує ім’я й кімнату. `telegram_username` оновлюється при
   кожному вході.

Запит живе 10 хвилин. Сесія — підписане cookie на рік з `resident_id` і
`session_version`; блокування збільшує `session_version`.

Свідомий ризик: людину можна вмовити натиснути «Так, це я» на чужий запит.
Кнопка підтвердження й короткий термін дії роблять це малоймовірним, а шкода
обмежена записами на пралку.

## Сповіщення

- Cron Trigger щохвилини (`* * * * *`) шукає записи, що починаються в
  найближчі 15 хв і ще не мають `reminded_at`, надсилає нагадування і ставить
  позначку, щоб не надіслати двічі.
- **Web Push**: ключі VAPID, шифрування повідомлень (RFC 8291) через WebCrypto
  прямо у Worker. На iPhone пуші працюють лише у встановленій PWA (iOS 16.4+),
  тому застосунок показує інструкцію «Додати на початковий екран».
- **Telegram**: бот пише людині напряму — вона вже натиснула «Start».
  Помилки відправки лише логуються й не ламають дію, як в Опереті
  (`ctx.waitUntil`).

## PWA

- `manifest.webmanifest`, іконки, `display: standalone`, світла тема.
- Власний невеликий `public/sw.js` (без `vite-plugin-pwa`, який погано
  поєднується з режимом фреймворку React Router): статичні файли — з кешу,
  сторінки — спершу мережа, без мережі — остання збережена версія з позначкою
  «станом на 14:20».
- Записатися чи скасувати без мережі не можна: це завжди запит до сервера.
- Розклад оновлюється опитуванням раз на 20 с, поки вкладка видима.
- QR-наліпка на кожній пралці веде на її сторінку.

## Маршрути першої версії

| Маршрут                 | Що робить                                                  |
| ----------------------- | ---------------------------------------------------------- |
| `/`                     | Мої записи, «Найближчий вільний час», три пралки           |
| `/book`                 | Програма чи тривалість → день → вільні початки по пралках |
| `/machines/:id`         | День пралки: записи й вільний час, «Почати зараз»          |

| `/login`, `/login/wait` | Вхід через бота                                            |
| `/welcome`, `/me`       | Ім’я, кімната, сповіщення                                  |
| `/telegram/webhook`     | Оновлення від бота, перевірка секретного заголовка         |

## Права

Усі перевірки — у `lib/permissions.ts`, кожна дія перевіряє їх на сервері.
Ролі: `resident` і `council`. Студрада скасовує будь-які записи й блокує людей;
першого члена студради призначає скрипт.

## Секрети

| -------------------------------------- | --------------------------------------------- |
| `SESSION_SECRET`                       | Підпис cookie; з нього ж секрет вебхука бота  |
